Ethics and Privacy Reflection

How ethical data use and user privacy were considered in the design of this application — including where it falls short.

Features that support ethical data use

1. Data minimisation — the website collects no personal data at all

The strongest privacy measure that I can do was to not collect the data in the first place. Looking at the create-event form, every field describes an event: title, course, category, date, time, mode, location, description and notes. There is no field for the organiser's name, no email address, no phone number, no student ID, and no attendee list.

2. No tracking of who looks at what

The application records which events exist. It does not record who searched for what, which events were viewed, how long anyone spent reading a description, or which categories a particular user filters by most often.

3. Accessibility as an ethical obligation

A website that excludes disabled students is not ethically neutral. Each image carries descriptive alt text so a screen reader can convey it; form fields are joined to their labels with for and id so that clicking a label focuses the right input.

4. Accurate representation of other people's events

Because student representatives enter events that belong to societies other than their own, so there is an duty not to misrepresent them. The update function exists so an event with the wrong time can be corrected rather than deleted and silently re-created, and the notes field gives the organisers a place to write whatever details they need to share.

Features that support data privacy

1. Access control on the page that can change data

The events directory is behind a login, so the create, update and delete controls are not available to an anonymous visitor.

The failure message is also part of the design. When a sign in fails the application says "Incorrect username or password" rather than "No such user". A message informing which half was wrong would confirm to an attacker what usernames exist on the system.

2. The session ends when the browser closes

The signed-in state is held in sessionStorage, not localStorage. The difference matters: localStorage survives until it is cleared, so a student who signed in on a library computer would still be signed in for the next person who sat down. sessionStorage is discarded when the tab closes.

3. The data never leaves the student's own device

Events are stored in the browser's localStorage on the machine where they were entered. There is no server, no database and no network request, so nothing a user types is transmitted anywhere. For a directory of public campus events this is a reasonable architecture, and it means a student can clear everything the application knows about them using their own browser settings, without asking anyone's permission. That is a meaningful form of user control over personal data.

Honest limitations of this implementation

Claiming this application is secure would itself be an ethical failure, so these are the places where the implementation is weaker than it may appear.

The login is not real security

The username and password are written in js/auth.js, which the browser downloads in full. Anyone can read them by opening the page source or the developer tools. The login restricts access in the sense that a casual visitor will not reach the admin controls, but it would not stop anyone who looked.

localStorage is not encrypted or protected

Data in localStorage is stored as plain text and is readable by anyone with access to the computer, and by any JavaScript running on the same origin. It is appropriate for public event listings but it would not be appropriate for anything private.

What I would add with more time

  • having an actual server with a database, properly hashed passwords and session tokens.
  • HTTPS, so data in transit cannot be read on a shared campus network.
  • A visible privacy notice stating what is stored and for how long.
  • A rule that removes events a set period after they finish, so the directory does not accumulate data that clutters the events list

Applying the course's ethical framework

The Week 8 tutorial sets out six ethical lenses — rights, justice, utilitarian, common good, virtue and care. I applied them to the one decision above that was a real trade-off: I removed the organiser contact email field.

  • Rights — does this honour everyone's rights? Students have a right to decide who can contact them. Storing addresses takes that decision away from an organiser who only wanted a listing.
  • Utilitarian — which option does the most good for the most people? The field saves a few students a search. A leak exposes every organiser. Small benefit spread thin, large harm concentrated.
  • Care — am I showing empathy for those affected? Not the average user, but the student whose event is a Pride society meet-up or a prayer group, for whom a contactable list is a different proposition.
  • Virtue — what does this decision make me? I could explain "we did not collect it" to a room of students. I could not comfortably explain "we collected it in case it was useful".

The rules this would sit under

  • The ACS Code of Professional Ethics places the primacy of the public interest above sectional interests, and requires competence and professionalism. The honest-limitations section is that clause in practice: describing a client-side login as real security would breach it more seriously than writing a weak login in the first place.
  • The Australian Privacy Principles require collection limited to what is reasonably necessary (APP 3), notice of what is collected and why (APP 5), and reasonable security (APP 11). This application meets APP 3 by collecting no personal data, but it has no privacy notice at all, so it would fail APP 5 — which is why a privacy notice is first on the list of things I would add.

Summary

The central lesson from building this website is that most privacy protection is decided on the design phase, not added afterwards. The decision not to collect organiser email addresses protects more students than any amount of security added later, because data that was never collected cannot be breached.

Being clear about what this application does not protect is part of the same responsibility. A client-side login that is described as real security would mislead whoever relied on it.
